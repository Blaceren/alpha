# TODAY_WORKSPACE.md — Alfa Trade Academy CRM (Phase 1B3)

Read-only операционный центр смены на маршруте `/today`.
Реализация: `src/domain/today/**` (деривация), `src/features/today/**` (рендер).
Связано: `TODAY_QUEUE_RULES.md` (основания), `DATA_PROVIDER_CONTRACT.md` (контракт), `USER_360.md` (разбор).

Today отвечает на восемь вопросов: что требует внимания сейчас, почему пользователь в очереди, насколько срочно, что рекомендуется, кто ответственный, какой срок, какие сигналы за этим стоят, как перейти в User 360. **Мутаций нет** — они отложены до Phase 1B4.

---

## 1. Две оси: основание и секция

Phase 1B1 моделировала «почему» как 13 параллельных очередей, в которых пользователь мог находиться одновременно. Это отвечает на вопрос «какая работа бывает», но не на «что открыть следующим». Phase 1B3 разводит два вопроса по осям:

- **Основание (`TodayBasisCode`) — почему.** Это те же 13 кодов из `config/queues.ts`. Пользователь может держать несколько. Они же — фильтр «Тип основания».
- **Секция (`TodaySectionKey`) — насколько срочно.** Пользователь попадает ровно в одну.

Ничего из Phase 1B1 не потеряно: предикаты членства (`BASIS_MEMBERSHIP`) те же, они лишь переосмыслены как основания, а не как очереди.

## 2. Членство в очереди

Пользователь попадает в Today **только при наличии хотя бы одного attention-основания** (`TODAY_ATTENTION_BASES`, 11 кодов).

`new_funded_users` и `repeat_funders` (`TODAY_SEGMENT_BASES`) **не являются основанием**: это ценностные сегменты — «кто пользователь», а не «что нужно сделать». Repeat funder без блокера, без срока и без остановки прогресса не требует сегодня ничего. Эти сегменты уже обслуживаются доменом Segments (`repeat_funders`, `frequent_repeat_funders`) и Users Workspace.

Спокойные пользователи в очередь не попадают вообще — не «в конце списка», а физически отсутствуют. На текущих фикстурах: 30 пользователей, 22 в очереди, 7 без единого сигнала остаются вне (D-43).

## 3. Canonical placement

Единственное место, где решается секция — `placeIn()`. Первое совпадение выигрывает, поэтому пользователь не может попасть в две секции.

| # | Секция | Правило |
|---|---|---|
| 1 | `overdue` — Просрочено | срок (SLA или follow-up) уже прошёл |
| 2 | `critical_now` — Критично сейчас | priority = critical |
| 3 | `today` — Требует внимания сегодня | priority = high, либо срок в пределах 24ч |
| 4 | `watch` — Наблюдение | основание есть, срок не горит |

`overdue` выше `critical_now` намеренно: пропущенный срок уже стоит денег, критическое состояние — ещё впереди. Критический пользователь в `overdue` сохраняет свой бейдж «Критический», поэтому выбор секции ничего не прячет.

Пустые секции не возвращаются: структура ради структуры — шум.

## 4. Сортировка

Внутри секции; порядок самих секций не сортируется никогда.

| Режим | Смысл |
|---|---|
| `urgency` (по умолчанию) | доменный `comparePriority`: полоса → индекс правила → SLA dueAt → severity → last action → stable user id |
| `last_activity` | «Сначала неактивные» — самый застоявшийся сверху; на экране триажа это и есть вопрос |
| `owner` | группировка по ответственному, без ответственного — в конец |

Детерминированность: `Math.random` не используется, время берётся только из `Clock` provider'а. Ручная сортировка не может увести критического пользователя из его секции — секции остаются на месте, а активный режим всегда подписан на контроле.

## 5. Причина строки

`basis.text` — предложение самого домена (reason активного сигнала), уже с числами: «Нет прогресса 80ч при доступном следующем уровне.». Абстрактное «Требует внимания» запрещено и покрыто тестом.

Порядок выбора заголовочного основания (`BASIS_RANK`) ставит **содержательные** основания выше **производных** (`TODAY_DERIVED_BASES`: `critical_attention`, `sla_breached`, `due_today`). Производные пересказывают то, что строка и так показывает бейджем приоритета и чипом срока; они становятся заголовком только если за пользователем нет ничего другого.

### Один факт — один раз (§10)

| Элемент строки | Что говорит | Почему не дублирует |
|---|---|---|
| Бейдж приоритета | насколько срочно | `priorityReasonCode` **не рендерится**: лестница приоритета и основания читают один каталог сигналов, поэтому reason — всегда более грубый пересказ причины. Поле остаётся в модели для паритета с `UserSummary` и для аудита лестницы в User 360 |
| Причина | почему | единственное главное утверждение |
| Evidence-чип | одно число | только `kind: "metric"`, и только если значения ещё нет в тексте причины |
| «Ещё основания» | что ещё есть | производные основания исключены |
| Чип срока | когда | не печатает SLA-ключ: причина и рекомендация уже сказали, о какой работе речь |

**Подпись рекомендации — из единого источника (D-52).** `TodayRecommendation` несёт только `code`;
формулировку даёт `config/labels`.`RECOMMENDATION_LABEL`, выведенная из
`RECOMMENDATION_CATALOG[code].title`. Вторая русская строка в read-модели не поедет — именно так одно
и то же действие раньше читалось на Today и User 360 по-разному (на трёх кодах). Users и User 360
резолвят подпись через тот же mapping, поэтому три экрана не могут разойтись.

## 6. Summary

Компактная строка из четырёх чисел, не dashboard: `totalAttention`, `critical`, `slaBreached`, `unassigned`.

Всегда описывает **текущую (отфильтрованную, permission-safe) очередь**, поэтому не может посчитать пользователя, которого роль не видит, и не может обещать работу, которой на экране нет. Ни графиков, ни дельт, ни целей — это вопросы другого продукта.

## 7. Фильтры и поиск

Семантика фильтров живёт в builder'е; React лишь передаёт выбор.

- `priority`, `basis` (тип основания), `sla`, `ownerId` (включая `unassigned`), `query`.
- Опции приходят из `TodayFilterOptions`, который provider строит по **реальной очереди этой роли** — контрол не предлагает значения, которое вернёт пусто, и не раскрывает основание, которого у роли нет. Пустая очередь → контролов нет.
- `scope: own | team` **не реализован**: mock-сессия даёт всем ролям один `emp_mock_admin`, а владельцы фикстур — `emp_ret1`/`emp_men1`, поэтому «моя очередь» всегда была бы пуста. Честный эквивалент — фильтр `ownerId` (D-44).
- Поиск идёт **только по разрешённой identity-проекции**: analyst по «Nina» находит 0, полный email не находит никто.

## 8. Операционное окно (§21)

`operationalWindow(clock)` = начало рабочих суток UTC → `clock.now`. На MOCK_NOW это `2026-07-13T00:00:00Z … 2026-07-13T09:00:00Z` (D-45).

Окно используется **только** для «что произошло сегодня» (`todayEvent`), через исправленный `from`/`to` таймлайна. Членство в очереди окном не считается: активный блокер, поднятый неделю назад, — это текущее состояние, и оно не устаревает. Поэтому модель разделяет:

- `lastActivityAt` — последнее значимое действие, сколь угодно давнее (состояние);
- `todayEvent` — событие внутри окна, либо `null` (событие).

## 9. Freshness

`TodayFreshness` = когда доска сгенерирована, плюс `ageMinutes`, посчитанный **provider'ом против его Clock**. React никогда не зовёт `Date.now()`.

Свежесть доски — это не возраст самого старого баланса: один пользователь с балансом двухнедельной давности не делает всю доску двухнедельной, пока каждый SLA на экране актуален. Возраст данных пользователя остаётся на его `financial.stale` и основании `data_quality_issues`.

`staleMode` — dev-превью (75 мин, выше порога `balance_data_stale.staleMinutes = 60`): mock выводит очередь из часов на каждом вызове и сам по себе устареть не может.

## 10. Приватность

Provider отдаёт уже спроецированный результат — запрещённое значение не строится, а значит не может утечь ни в DOM, ни в aria/title, ни в data-атрибут.

- **Финансы.** Баланс проецируется только для оснований, где он помогает триажу (`TODAY_BASES_WITH_FINANCIALS`: checkpoint, качество данных) — иначе `financial: null`, и строка не показывает баланс вообще. `null`, а не «hidden»-проекция: `FinancialHiddenReason` отвечает «нет данных» или «нет прав», и ни то, ни другое не было бы правдой для админа, которому баланс просто не нужен.
- **Реконструкция.** `checkpoint_approaching` и `rapid_balance_decline` объясняются процентом от опубликованной сетки ($100 на L10), то есть «осталось 5%» + сетка = $95. Для ролей без exact-прав их текст заменяется нейтральным, а evidence отбрасывается. Правило вынесено в `domain/financial/financially-derived.ts` и общее с User 360 (D-46).
- **Identity.** Очередь — список, поэтому `context: "list"`: полный email не строится ни для кого. analyst → псевдоним, content_manager → без идентификации; `userId` остаётся всегда — это платформенный идентификатор и способ открыть профиль.
- **Смена роли** сбрасывает поисковую строку: она могла называть человека, которого новая роль не видит, и повторное применение задало бы проекции вопрос, ради отказа на который она существует.

## 11. Состояния

| Состояние | Что показывает |
|---|---|
| Loading | Skeleton в реальной геометрии (шапка, summary, секция, строки) — без прыжка layout |
| Error | Понятное сообщение; «Повторить» только если provider назвал чтение retriable; h1 сохраняется, рабочая дата — нет (её сообщает provider, а чтение не удалось) |
| Stale | Ненавязчивый баннер с возрастом; очередь остаётся полностью доступна — слегка несвежая работа всё ещё работа |
| Нет работы | «На сегодня нет пользователей, требующих внимания» — это результат, а не сбой. Без иллюстраций и маркетинга |
| Фильтры пусты | «По выбранным фильтрам ничего не найдено» + «Сбросить фильтры» |
| Пустая база | «В базе пока нет пользователей» |
| Нет доступа | Только при `unauthorized`. `/today` виден всем 9 ролям, поэтому пустая очередь **никогда** не является рассказом о правах |

## 12. Доступность

Один `h1`; секции — `<section>` с `<h2>`; очередь — семантический список. Приоритет и SLA всегда несут текст, не только цвет. Причина доступна скринридеру (`Причина:` — sr-only). У ссылки в профиль пользователь в accessible name: «Открыть профиль: Nina Chmiel», а не 22 одинаковые ссылки. Фильтры подписаны, активная сортировка озвучена в имени контрола, mobile Sheet управляется клавиатурой (Radix), touch targets ≥44px, 200% zoom пригоден, критический текст не живёт только в tooltip.

## 13. Границы

Реализовано: read-only очередь, основания, группировка, сортировка, summary, фильтры, поиск, состояния, desktop/tablet/mobile/zoom, переход в User 360.

Не реализовано (Phase 1B4+): любые мутации **на этом экране** (assignment UI в Today не добавлен, D-74), выполнение рекомендаций, задачи, закрытие блокеров/сигналов, кейсы, заметки, массовые операции, drag-and-drop, коммуникации, автоматизации, backend, база, Prisma, Pocket API, production auth.

**Owner: согласованность (Phase 1B4-C).** Назначение owner делается на User 360. Today читает **effective
owner** (baseline, перекрытый overlay, D-70) через `buildTodayWorkspace(effectiveUsers())`, поэтому row
owner, owner-фильтр (включая `unassigned`), `summary.unassigned` и `filterOptions.owners` согласованно
показывают нового владельца при следующем provider read. `filterOptions.owners` по-прежнему строятся из
реальной очереди роли (мёртвых опций нет). Live cross-tab sync не реализован (D-72).
