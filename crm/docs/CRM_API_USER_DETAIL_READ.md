# CRM_API_USER_DETAIL_READ.md — production `/users/[userId]`

Зафиксировано срезом «Frontend CRM User Detail API Slice 2». Вторая подключённая
production-способность CRM после списка пользователей.

> Это **основа** карточки учащегося, а не полный User 360. Владелец, заметки,
> финансы, активность, таймлайн, рекомендации и жизненный цикл по-прежнему
> отсутствуют — у backend для них нет источника.

## 1. Backend-контракт

Источник: `alfa-trade-academy-v2`, `docs/CRM_USER_DETAIL_V1.md`,
HEAD `95b9c83473c9526347dc204611b96417483fe84e`.

```
GET /api/crm/v1/users/{userId}
```

- `userId` — каноническое положительное десятичное целое, максимум `2147483647`;
- query-параметры **запрещены** (любой ключ → 400);
- граница «только учащиеся»: `User.role = "user"`;
- неизвестный учащийся, аккаунт сотрудника и системный аккаунт → **одинаковый 404**;
- читать может любая из девяти StaffRole;
- полный email зависит только от `view_identity_full_email`;
- `reveal_pii` сам по себе полный email не даёт;
- `Cache-Control: no-store` и `X-Request-Id` на каждом ответе.

Реализация backend не копировалась. Frontend валидирует ответ независимо.

## 2. Точный третий rewrite

API-режим проксирует ровно **три** определения:

```
/api/crm/v1/session          →  ${CRM_BACKEND_ORIGIN}/api/crm/v1/session
/api/crm/v1/users            →  ${CRM_BACKEND_ORIGIN}/api/crm/v1/users
/api/crm/v1/users/:userId    →  ${CRM_BACKEND_ORIGIN}/api/crm/v1/users/:userId
```

В mock-режиме список rewrite пустой.

`:userId` — **ровно один сегмент**, не `:userId*` и не catch-all. Поэтому
`/api/crm/v1/users/123/notes`, `/123/owner`, `/123/audit` и `/123/extra` **не
проксируются** и отвечают 404 на уровне Next.

Один некорректный сегмент (`/api/crm/v1/users/mock_user_1`) **проксируется**, и
backend возвращает свой канонический 400 — валидация идентификатора для прямых
API-запросов принадлежит backend, а не прокси. Это осознанное решение, а не
упущение.

Как и раньше: нет CORS, нет переписывания Domain у cookie, нет секретных
заголовков, origin backend в браузер не попадает.

## 3. Строгий frontend-DTO

`src/data/contracts/api/user-detail.ts`, Zod, `.strict()` на каждом уровне:

```ts
{ userId: string;                                   // непрозрачный, остаётся строкой
  displayName: string;                              // непустой после trim
  email: { value: string; visibility: "full" | "masked" };
  status: "active" | "blocked";
  level: number;                                    // целое
  xp: number;                                       // целое ≥ 0
  emailConfirmed: boolean;
  createdAt: string; }                              // ISO datetime
```

Отклоняются: неизвестные поля (`employeeId`, `role`, `permissions`,
`effectivePermissions`, `ownerId`, `noteCount`, `balance`, `netDeposits`,
`lastMeaningfulActionAt`, `lifecycleStage`, `updatedAt`, `currentTask`,
`achievements`, `timeline`, `recommendations`, `passwordHash`), неизвестные
`status`/`visibility`, дробные `level`/`xp`, отрицательный `xp`, невалидная дата.

Ошибки: `{ code: "invalid_input" | "unauthorized" | "not_found" | "internal",
messageKey, requestId }`. Авторитетен статус-код; `messageKey` пользователю не
показывается никогда, показывается только `requestId`.

## 4. Валидация идентификатора на фронтенде

`src/data/contracts/api/user-id.ts` — чистая функция, повторяющая принятый
публичный контракт backend:

```
/^[1-9][0-9]{0,9}$/   и затем   1 ≤ value ≤ 2147483647
```

Отклоняются: пустая строка, `0`, отрицательные, `+1`, ведущие нули (`01`, `007`),
дробные, экспонента, пробелы, mock-идентификаторы, значения вида `employeeId`,
слишком большие числа. `parseInt` **не используется**: он принял бы `12abc` и
`1.9` по числовому префиксу — именно та мягкость, ради которой этот guard и
существует.

Идентификатор остаётся строкой на всём пути: `Number()` применяется только для
сравнения диапазона, дальше передаётся исходная каноническая строка.

Прямой заход на некорректный `/users/[id]`:

- **не выполняет запрос к API** (проверено unit-тестом и E2E);
- показывает «Некорректный идентификатор пользователя»;
- сохраняет ссылку «← К списку пользователей».

## 5. Клиент

`src/application/api/user-detail-client.ts` — только относительный путь, без
query-строки, `credentials: "same-origin"`, `cache: "no-store"`, таймаут 8 с,
склейка с `AbortSignal` вызывающего, отмена устаревших запросов.

Отображение: `200 valid → success`, `200 malformed / не-JSON → malformed_response`,
`400 → invalid_input`, `401 → unauthenticated`, `403 → forbidden`,
`404 → not_found`, `5xx / сеть / таймаут → upstream_unavailable`.
Тело ответа, ошибка Zod и текст исключения не логируются и не рендерятся.

## 6. Способность провайдера

`ApiCrmDataProvider` после этого среза имеет **ровно два** метода:

```
listUsers        (Slice 1)
getUserDetail    (этот срез)
```

Тест проверяет прототип: `["getUserDetail", "listUsers"]` и ничего больше.
Мутаций нет, `getCrmMutations` в API-режиме по-прежнему недоступен, любая другая
способность падает через `UnsupportedApiCapability`. Модули не импортируют
`MockCrmDataProvider`, фикстуры и mock-`UserSummary`.

## 7. Композиция маршрутов

| Маршрут (API-режим) | Поведение |
| --- | --- |
| `/users` | production-список (Slice 1) |
| `/users/{валидный id}` | production-карточка учащегося |
| `/users/{некорректный id}` | локальное состояние, запрос не отправляется |
| `/users/{id}/…` | вложенного маршрута нет — 404 приложения |
| остальные разделы CRM | принятое отложенное состояние |

`children` (mock-страницы) в API-режиме по-прежнему **не рендерятся вообще**,
поэтому `User360Workspace` не монтируется никогда.

**Mock-режим не изменён**: `/users/[id]` продолжает открывать полный
`User360Workspace`, переключатель ролей и localStorage-роль работают как раньше.

## 8. Навигация из списка

Строки production-списка теперь содержат настоящую ссылку
`/users/{userId}` — не click-only `div`: она доступна с клавиатуры и её
accessible name — имя учащегося. Непрозрачный идентификатор подставляется
дословно (тест проверяет, что `"0071"` не превращается в `"71"`). Поиск и
пагинация не изменились; в mock-режиме навигация прежняя.

## 9. Видимые поля карточки

Шапка: ссылка назад, `displayName`, бейдж статуса.
Блок «Идентификация»: email + признак `Полный email`/`Скрытый email`,
подтверждение email, дата регистрации.
Блок «Прогресс»: уровень, XP.

`active → Активен`, `blocked → Заблокирован`,
`emailConfirmed true → Подтверждён`, `false → Не подтверждён`.
Дата — детерминированный `DD.MM.YYYY` в UTC.

Отсутствуют **целиком** (секции не рендерятся пустыми, а отсутствуют):
владелец, заметки, финансы, депозиты, последняя активность, таймлайн,
рекомендации, приоритет, сегменты, задачи, кейсы, достижения, текущая задача,
страна/локаль/таймзона/источник привлечения. Нет вкладок для недоступных данных,
нет заявления о «360°», нет ни одного действия-мутации (редактирование,
блокировка, сброс пароля, удаление). `userId` не отображается, `employeeId` и
`effectivePermissions` не отображаются.

## 10. Состояния

loading · populated · invalid id · unauthenticated · forbidden · not found ·
upstream unavailable · malformed · retrying.

- **401** → `router.replace("/login?reason=session_required")`, данные учащегося
  на экране не остаются;
- **403** → «Нет доступа к данным CRM» + опционально `requestId`;
- **404** → «Пользователь не найден», одинаково для несуществующего учащегося,
  аккаунта сотрудника и системного аккаунта (backend их не различает — и UI не
  должен);
- **400** → «Некорректный идентификатор пользователя»;
- **5xx / сеть / таймаут** → «Сервис недоступен» + «Повторить»;
- **malformed 200** → «Некорректный ответ сервиса», частичный рендер не
  выполняется.

Повтор сохраняет `userId`; во время запроса кнопка «Повторить» исчезает, поэтому
второй клик физически невозможен, а не просто игнорируется.

## 11. Честность проекции email

Фронтенд рендерит **ровно то**, что вернул backend. Он не восстанавливает
полный адрес, не маскирует повторно и не выводит видимость из роли.
`email.visibility` используется только как подпись.

Регрессия: сессия `crm_admin` с `effectivePermissions=[]` + masked-ответ backend →
UI показывает только маску, полный адрес отсутствует в DOM. Подставленная
localStorage-роль на проекцию не влияет.

## 12. Тестовая топология

Настоящий backend не запускался. Прежний детерминированный stub на стандартной
библиотеке Node (`tests-e2e-session/support/session-stub.mjs`, loopback
`127.0.0.1:3110`) расширен ровно на `GET /api/crm/v1/users/{один сегмент}` с
синтетическими данными; вложенные пути он отклоняет. Состояние выбирается
тестовой cookie `ata_test_crm_user_detail_state`; в production-коде нет ни
тестовых заголовков, ни тестовых query-параметров. Ответы содержат
`Cache-Control: no-store` и `X-Request-Id`. Базы данных нет.

## 15. Заметки в карточке пользователя (CRM User Notes v1)

Производственная карточка `/users/[userId]` теперь включает раздел «Заметки»,
ограниченный правами. Разделы «Идентификация» и «Прогресс» не изменились.

- Список рендерится только при `view_user_notes`.
- Композер рендерится только при `create_user_notes`.
- Права проверяются независимо: ни одно не подразумевает другое.
- `edit_user_notes` не даёт ни чтения, ни создания — оно зарезервировано за
  будущими операциями над существующей заметкой.
- Без обоих прав раздел не монтируется и ни один запрос не отправляется.
- Видимость определяется только `effectivePermissions`, никогда — именем роли.

Производственная карточка также включает раздел «Ответственный» (Owner v1):
текущий владелец виден каждому StaffProfile, а управление назначением
монтируется только при `assign_owner`. Полный контракт:
`docs/CRM_API_USER_OWNER.md` (требуется миграция бэкенда 32).

Подключённые возможности API-провайдера теперь: список пользователей, карточка
пользователя, чтение заметок, создание заметки, чтение владельца, список
кандидатов и назначение владельца. Audit, финансы и активность остаются
отложенными.

Ошибки заметок не стирают успешно загруженную карточку: 403 и 500 остаются
локальными для раздела, тогда как 401 и 404 — ответы уровня учётной записи.

Полный контракт: `docs/CRM_API_USER_NOTES.md`. Требуется миграция бэкенда 31.
