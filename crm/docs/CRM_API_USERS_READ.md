# CRM_API_USERS_READ.md — production-режим: подключённый список пользователей

Зафиксировано срезом «Frontend CRM Users API Slice 1». Первая реальная
production-выдача данных CRM после принятой границы сессии.

## 1. Backend-контракт

Источник: `alfa-trade-academy-v2`, `docs/CRM_USERS_V1.md`,
HEAD `7a62cbf4e01a01f88d0e605ad7ae15ff7dd2f7e2`.

```
GET /api/crm/v1/users?limit=&cursor=&search=
```

- `limit` — целое 1–100, по умолчанию 25;
- `cursor` — непрозрачная строка, максимум 512 символов;
- `search` — обрезанная строка, максимум 100 символов;
- неизвестные ключи → `400 invalid_input`.

Порядок стабильный (`createdAt DESC, id DESC`), пагинация только курсорная,
заголовки `Cache-Control: no-store` и `X-Request-Id` на каждом ответе.

Реализация backend во frontend **не копировалась**. Frontend валидирует ответ
независимо: расхождение контракта или подмена прокси должны падать закрыто, а не
доезжать до экрана.

## 2. Точный rewrite

API-режим проксирует ровно два пути:

```
/api/crm/v1/session  →  ${CRM_BACKEND_ORIGIN}/api/crm/v1/session
/api/crm/v1/users    →  ${CRM_BACKEND_ORIGIN}/api/crm/v1/users
```

В mock-режиме список rewrite пустой.

Wildcard нет: ни `/api/crm/v1/:path*`, ни `/api/:path*`. Оба источника —
точные пути, поэтому `/api/crm/v1/users/123`, `/api/crm/v1/users/extra` и
`/api/crm/v1/user` **не проксируются** и отвечают 404 (проверено и unit-тестом
против настоящего конфига, и E2E в браузере). `/api/auth/*` и `/api/health`
недоступны. Cookie остаётся host-only, CORS не настраивается, секретных
заголовков нет, origin backend в браузер не попадает.

## 3. Строгий frontend-DTO

`src/data/contracts/api/users.ts`, Zod, `.strict()` на каждом уровне:

```ts
{ items: Array<{
    userId: string;                                   // непрозрачный
    displayName: string;                              // непустой после trim
    email: { value: string; visibility: "full" | "masked" };
    status: "active" | "blocked";
    level: number;                                    // целое
    emailConfirmed: boolean;
    createdAt: string;                                // ISO datetime
    owner: { displayName: string } | null;            // только displayName, либо null
  }>;
  nextCursor: string | null; }
```

Отклоняются: неизвестные поля (`employeeId`, `ownerId`, `noteCount`, `balance`,
`netDeposits`, `lastMeaningfulActionAt`, `lifecycleStage`, сырые колонки
`updatedAt`/`passwordHash`/`xp`), неизвестные `status`/`visibility`, невалидная
дата, пустой `userId`, числовой `userId`, **дубликаты `userId` в одном ответе**.

Объект `owner` **строгий** и содержит **ровно** `displayName` (живое
`StaffProfile.displayName`, непустое после trim). Это НЕ богатый owner-контракт
карточки (`crmOwnerIdentitySchema`, у которого есть `employeeId`): строка списка
только называет владельца, но не даёт на него действовать, поэтому его `id` она
не узнаёт. `owner: null` покрывает **оба** состояния — «строки нет» (pristine) и
«строка есть, но `ownerId=null`» (снят после назначения); список их **не
различает**. `owner` — обязательный ключ (backend всегда его присылает), поэтому
его отсутствие — это дрейф и падает закрыто. Внутри `owner` отклоняются любые
`employeeId`, `ownerId`, `ownerVersion`, `StaffRole`/`role`, email, `status`,
`permissionVersion`, `createdAt`/`updatedAt`.

`userId` остаётся строкой: он не парсится как число, не участвует в арифметике и
используется только как React-key и идентичность строки.

Ошибки: `{ code: "invalid_input" | "unauthorized" | "internal", messageKey,
requestId }`. Авторитетным остаётся статус-код; `messageKey` — это копирайт
backend, а не CRM, и пользователю не показывается никогда. Показывается только
`requestId` как код обращения.

## 4. Клиент

`src/application/api/users-client.ts` — относительный путь,
`credentials: "same-origin"`, `cache: "no-store"`, таймаут 8 с, склейка с
`AbortSignal` вызывающего. Сериализуются **только** `limit`, `cursor`, `search`
и `owner` — в детерминированном порядке `limit → cursor → search → owner`;
`offset`, `page`, `sort`, `segment`, `status`, `employeeId`, `role`,
`permissions` не сериализуются никогда.

`owner` пишется **только** для значений `mine`/`unassigned`. `all` (как и
пропуск/неожиданное значение) **не пишет ничего** — канонический запрос без
`owner` соответствует умолчанию backend «пропуск = all», а невалидное owner-
значение frontend физически не может отправить (см. §15).

Отображение: `200 valid → success`, `200 malformed / не-JSON → malformed_response`,
`400 → invalid_input`, `401 → unauthenticated`, `403 → forbidden`,
`5xx / сеть / таймаут → upstream_unavailable`. Ни тело ответа, ни ошибка Zod, ни
текст исключения не логируются и не рендерятся.

## 5. ApiCrmDataProvider

`src/data/api/api-crm-data-provider.ts` реализует **одну** способность —
`listUsers`. Он сознательно **не** реализует широкий `CrmDataProvider`: тот
интерфейс сформирован mock-продуктом (Today, User 360, заметки, владелец, аудит,
очереди), и «реализовать» его можно было бы только методами, которые лгут или
бросают. Сужение по способности делает недоступные операции недостижимыми на
уровне типов, а не только защищёнными в рантайме.

Дополнительно `assertApiCapability` бросает `UnsupportedApiCapability` для любой
неподдерживаемой операции — пустой список никогда не возвращается, потому что
«у пользователя нет заметок» и «заметки ещё не подключены» не должны выглядеть
одинаково.

Модуль не импортирует `MockCrmDataProvider`, не обращается к фикстурам и не
строит mock-`UserSummary` (проверяется тестом по строкам импортов).
`getCrmMutations` в API-режиме по-прежнему недоступен.

Провайдер конструируется только под подтверждённой сессией: единственный его
потребитель рендерится внутри authenticated-ветки `SessionBoundary`.

## 6. Ограниченная оболочка и маршруты

API-режим монтирует ровно один маршрут — **`/users`**.

- `/users` → `ApiShell` + production-список. В шапке: бренд ATA CRM, имя
  сотрудника, безопасная подпись роли и **один** пункт навигации «Пользователи».
- любой другой маршрут, включая **`/users/[id]`** → состояние «Раздел ещё не
  подключён» с безопасной ссылкой на `/users`.

`children` (mock-страницы) в API-режиме не рендерятся вообще, поэтому
`User360Workspace` не монтируется и запрос к несуществующему User 360 не
выполняется. `/users` сопоставляется точно, а не по префиксу — именно это
оставляет `/users/123` отложенным.

Оболочка не показывает: RoleSwitch, mock-счётчики, Today/Аудит/Финансы/Задачи/
Кейсы/Заметки/Настройки, фиктивные уведомления, `employeeId`, список разрешений,
origin backend, детали окружения.

> **Обновление (Frontend CRM User Detail API Slice 2).** Строки списка теперь
> открывают production-карточку `/users/{userId}` настоящей ссылкой (доступной с
> клавиатуры, с именем учащегося в accessible name). Список пользователей и
> основа карточки — **единственные** подключённые способности; заметки,
> владелец, финансы, активность и таймлайн по-прежнему отложены. Подробности:
> `docs/CRM_API_USER_DETAIL_READ.md`.

## 7. Колонки списка

Имя · Email · Статус · Уровень · Email подтверждён · **Ответственный** ·
Регистрация.

`active → Активен`, `blocked → Заблокирован`,
`emailConfirmed true → Подтверждён`, `false → Не подтверждён`.
Дата — детерминированный `DD.MM.YYYY` в UTC (не зависит от локали хоста).
Столбец «Ответственный» стоит **после** «Email подтверждён» и **перед**
«Регистрация»; см. §15.

Нет и не будет в этом срезе: счётчика заметок, финансов, последней
активности, рекомендации, приоритета, сегмента, сортировки (в т.ч. по
владельцу), mock-фильтров, **общего количества** и «страница X из Y» —
backend не отдаёт total, поэтому показывается только позиция «Страница N».

`userId` не отображается: он служит только React-key.

## 8. Поиск и разрешения

Авторитет — `session.effectivePermissions`, не роль.

- есть `view_identity_full_email` → подпись «Имя или email», email-поиск
  отправляется;
- нет → подпись «Имя», значение с `@` **не отправляется**, показывается локальное
  сообщение «Поиск по email недоступен для вашей роли». Backend остаётся
  авторитетным: локальный отказ лишь экономит round-trip и объясняет причину.

Роль `crm_admin` с пустыми `effectivePermissions` аффорданса email-поиска **не
получает** — проверено unit-тестом и E2E. Значение из localStorage
(`ata-crm.mock-role.v1`) на API-режим не влияет.

Поиск обрезается, ограничен 100 символами, пустой сбрасывает на первую страницу,
отправка сбрасывает историю курсоров. Отправка явная (submit), устаревшие ответы
не заменяют более новые (счётчик запросов + `AbortController`).

## 9. Курсорная пагинация

Только курсоры backend, размер страницы 25.

«Следующая» использует `nextCursor`; «Предыдущая» — стек курсоров в памяти
клиента (у backend нет обратного курсора). На первой странице «Предыдущая»
отключена, на последней — «Следующая». Курсор не декодируется, не логируется, не
отображается и не сохраняется в localStorage. Offset не используется. Дублирующие
параллельные запросы отсекаются.

## 10. Поведение при ошибках

| Ответ | Поведение |
| --- | --- |
| 401 | `router.replace("/login?reason=session_required")`, ранее показанные строки не остаются |
| 403 | «Нет доступа к данным CRM», опционально `requestId` |
| 400 | «Некорректный запрос», форма поиска сохраняется |
| 5xx / сеть / таймаут | «Сервис недоступен» + «Повторить» |
| malformed 200 | «Некорректный ответ сервиса», частичный рендер не выполняется |

Повтор — строго один запрос за раз. Fallback на mock отсутствует во всех случаях.

## 11. Mock-режим не изменён

`MockCrmDataProvider` по-прежнему обслуживает mock-`/users`; богатые колонки,
фильтры, сортировки, пагинация, `/users/[id]` с User 360, переключатель ролей и
localStorage-роль работают как раньше. Production-контракт **не** упрощал
mock-продукт: production-список — отдельная фича (`src/features/users-api`), а не
переписанный `UsersWorkspace`.

## 15. Обновление (Frontend CRM Users Owner Column & Filters)

Срез подключает единственное реляционное поле, которое backend может доказать —
текущего владельца учащегося — как отдельный столбец и как фильтр списка.
Backend-контракт: `alfa-trade-academy-v2`, `docs/CRM_USERS_V1.md`, HEAD
`56c817bdf8f601a97c5b04957fbe5c588a13672f`. **Новый rewrite не добавлен** и не
нужен: `owner` — это query-параметр на уже существующем пути `/api/crm/v1/users`,
поэтому API-режим остаётся ровно на **шести** rewrite (session, users, user
detail, user notes, owner candidates, user owner). Миграций нет.

### Поле owner в DTO

Строгий, только `displayName`, либо `null` (см. §3). `null` — это оба состояния
(pristine и persisted-`ownerId=null`); список их не различает. Внутри `owner`
отклоняются `employeeId`, `ownerId`, `ownerVersion`, `StaffRole`/`role`, email,
`status`, `permissionVersion`, любые timestamp. Богатый owner-контракт карточки
(`crmOwnerIdentitySchema` с `employeeId`) в строку списка **не адаптируется**.

### Фильтры

Ровно три значения, точное соответствие как у backend:

| Значение | Метка | URL | Запрос |
| --- | --- | --- | --- |
| `all` | «Все» | параметр отсутствует (канон) | `owner` не отправляется |
| `mine` | «Мои» | `?owner=mine` | `owner=mine` |
| `unassigned` | «Без ответственного» | `?owner=unassigned` | `owner=unassigned` |

- `all` — умолчание: пропуск и явный `all` эквивалентны, но **frontend никогда не
  пишет `owner=all`** ни в URL, ни в запрос.
- `mine` резолвится backend из аутентифицированного `StaffProfile`; **frontend
  никогда не отправляет employee id** — на проводе только литерал `mine`.
- `unassigned` включает оба backend-состояния (нет строки ИЛИ `ownerId=null`).
- `assigned` и выбор конкретного владельца в этом срезе **не поддержаны**.
- Нет сортировки по владельцу; запрос owner-кандидатов из списка **не делается**.

Контрол — доступный нативный `<select>` с меткой «Ответственный» (один на все
ширины, цель ≥44px, всегда ровно одно выбранное значение). Показан **каждому**
аутентифицированному сотруднику: **без** гейта `assign_owner`, без ветвления по
`StaffRole`, без запроса кандидатов. Пояснение для «Мои» — «Закреплённые за
мной». Фильтр виден и сохраняет выбранное значение во всех состояниях (загрузка,
400/401/403/500/malformed).

### URL-состояние и канонизация

`owner` — единственный shareable-параметр URL (существующий поиск в URL **не**
переносится и не переименовывается). Значение читается из URL при монтировании
(refresh/шаринг `?owner=mine` восстанавливаются), браузерные назад/вперёд
восстанавливают фильтр через `popstate`. Хранилищ не используется: ни
`localStorage`, ни `sessionStorage`, ни cookie.

Канонизация (через `replace`, без записи в историю): входящий `owner=all`,
повторный `owner`, пустое/иное регистр/мусорное значение схлопываются в `all` и
удаляются из URL; невалидное значение на backend **не** уходит и в UI сырым не
показывается. Корректный одиночный `?owner=mine` уже каноничен — лишнего
переписывания истории нет. Смена фильтра пользователем — это `push` (новая запись
истории), поэтому назад возвращает предыдущий фильтр.

### Сброс пагинации

Смена `owner` (или назад/вперёд, меняющий `owner`): прерывается запрос в полёте,
очищаются строки, стек курсоров сбрасывается в `[null]`, позиция — «Страница 1»,
запрос уходит с новым фильтром; **поиск сохраняется**. Смена поиска: `owner`
сохраняется, курсоры сбрасываются. Смена сотрудника сессии: очистка строк и
пагинации, рефетч по текущему URL. Строки предыдущего фильтра во время загрузки
нового не показываются; задержавшийся ответ прежнего фильтра не перезаписывает
текущие строки (счётчик запросов + `AbortController`).

### Столбец и мобильная выдача

Столбец «Ответственный» — после «Email подтверждён», перед «Регистрация».
Назначено → `owner.displayName`; `null` → «Не назначен». Ни `employeeId`, ни
`ownerVersion`, ни `StaffRole`, ни email, ни статуса, ни таймстампа, ни контрола
редактирования/сортировки/выбора. Длинное имя переносится и остаётся полностью
доступным через `title`. Production-список остаётся единой адаптивной таблицей:
широкое содержимое скроллится **внутри своего контейнера**, документ по
горизонтали не переполняется; на 320px и при 200% зума значение владельца и
фильтр остаются доступны (это осознанно НЕ отдельные mock-карточки — их
переработка не входит в срез).

### Пустые состояния

- `mine` без строк: «За вами пока не закреплены пользователи.»
- `unassigned` без строк: «Все пользователи закреплены за ответственными.»
- при **непустом** поиске приоритет у существующего сообщения поиска;
- `all` без строк: прежнее «Пользователи не найдены.»

Сырые значения запроса и employee id в пустых состояниях не раскрываются.

### Mock-режим

Поведение mock не изменено (§11): mock-фильтры владельца, выбор конкретного
владельца, User360 и mock-скриншоты остаются как были. Production-набор фильтров
у́же mock — и это нормально. Fallback на mock отсутствует.

### Провайдер

Поверхность провайдера — те же **семь** методов: `owner` протянут в существующий
`listUsers` (нового метода нет, `listUsersByOwner`/`listMyUsers` не заведены).

### Совместимость рантайма

Изолированный DEV-рантайм остаётся **остановленным**, БД — неизменной, до
финального smoke-теста совместимости. Backend/Academy не менялись.
