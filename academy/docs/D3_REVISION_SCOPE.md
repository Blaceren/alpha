## 1. Почему report-kind сам по себе review-gated

Уровень с `kind: "report"` — единственный вид уровня, на котором пользователь **производит работу
для внешней проверки**, а не потребляет материал и не проходит самопроверяемый тест:

- урок завершается фактом просмотра — проверка объективна и локальна (DD-249);
- тест завершается правильными ответами — проверка объективна и локальна (D2B);
- отчёт завершиться сам **не может**: единственное локально проверяемое свойство — «есть ли что
  проверять» (структурное правило готовности, DD-274). Проверить *содержание* работы локально
  нельзя, не выдумав торговую rubric — прямой запрет DD-268.

Поэтому review-gating — **свойство самого kind**, а не отдельного флага: report-уровень по своей
природе завершается только внешним `approved` (DD-265). Отчёт без проверки был бы формой, которую
можно заполнить чем угодно, — и «серьёзная учебная рабочая поверхность» превратилась бы в формальность.

### 1.1 Почему `mentorReview: false` у уровня 3 — не противоречие

Поле `mentorReview` в curriculum fixture описывает **дополнительную mentor-review механику
practical-уровней** — отдельный будущий контур (D3-E/D3-F, OQ-4), где наставник сопровождает
practical-работу. Оно **не является** универсальным признаком «этот уровень требует проверки»:

- у report-уровня требование проверки **встроено в kind** и не нуждается в флаге;
- у practical-уровня флаг добавляет механику **поверх** его собственной природы.

Читать `mentorReview: false` у уровня 3 как «отчёт не проверяется» — значит перепутать флаг
дополнительной механики с природой уровня. **Curriculum fixture не изменяется.** Level 3 остаётся
единственным report-уровнем первого среза; вопрос «L3 против L14» закрыт и повторно не открывается.

## 2. Lifecycle D3-C

D3-C покрывает **только** цикл доработки:

```
                       вердикт (dev/test adapter, §5)
   ┌────────────────┐ ───────────────────────────────▶ ┌────────────────────┐
   │ pending-review │                                   │ revision-requested │
   └────────────────┘ ◀─────────────────────────────── └────────────────────┘
           ▲                повторная отправка                    │
           │                                                      │ правка любого раздела
           │                                                      ▼
   ┌────────────────────┐   правило готовности ∧ есть   ┌───────────────────┐
   │ ready-to-resubmit  │ ◀──────────────────────────── │ editing revision  │
   └────────────────────┘   изменения после вердикта    └───────────────────┘
```

| Состояние | Природа | Смысл |
|---|---|---|
| `pending-review` | **хранится** | пользователь отметил отчёт отправленным в этом браузере (DD-266) |
| `revision-requested` | **хранится** (вместе с feedback) | проверка вернула работу с комментарием |
| `editing revision` | **вычисляется** | статус `revision-requested`, поля снова редактируемы |
| `ready-to-resubmit` | **вычисляется** | правило готовности выполнено ∧ черновик изменён после вердикта |

Принцип D3-B сохраняется: **хранятся только факты, состояния презентации выводятся**
(`REPORT_STATE_MACHINE.md`). `editing revision` и `ready-to-resubmit` — производные, их персистенция
создала бы расхождение флага с записями, которые он описывает.

Правило `ready-to-resubmit` — **структурное, не оценочное**: то же правило готовности DD-274 плюс
факт «черновик отличается от отправленной версии». *(Уточнение D3-C-B, DD-290: факт изменения несёт
отдельный счётчик `meaningfulRevision`, растущий только при содержательном — нормализованном —
изменении; технический `revision` остаётся ключом autosave, и whitespace-правка сохраняется, но
изменением не считается.)* Какие именно разделы изменены — **не проверяется**: отмеченные разделы —
подсветка внимания, а не валидатор. Требовать изменения именно отмеченных мест значило бы выдумать
enforcement, которого у curriculum нет, и наказать пользователя, который не согласен с одной из
пометок.

**Не входят в D3-C:** `approved` (внешнее событие — D3-D), автоматический вердикт любого вида,
mentor thread, очередь проверки. Повторная отправка возвращает статус **ровно в `pending-review`** —
без «повторная проверка быстрее», без приоритетов, без счётчика попыток в UI.

### 2.1 Что происходит с уже отправленной версией

Версия истории **не заводится** (version-history UI — non-scope). Локальная запись отчёта — одна:
при вердикте `revision-requested` она снова становится редактируемой, и пользователь дорабатывает
**свою же работу**, а не пишет новую. Интерфейс говорит это прямо: все записи и итоговое наблюдение
сохранены, ничего не потеряно и не сброшено. Отдельная копия «как было при отправке» не хранится и
не обещается.

## 3. Блокировка уровня 4

Ничего не меняется относительно DD-272:

- уровень 3 **не завершается** ни при `pending-review`, ни при `revision-requested`,
  ни при повторной отправке — `ata.lesson-progress.v1` не пишется;
- уровень 4 «Контрольная точка $50» остаётся закрыт, потому что уровень 3 не завершён,
  а не потому, что его «заперли»;
- каноническая фраза остаётся: **«Уровень 4 откроется после одобрения отчёта»**;
- фраза по-прежнему **выводится** из резолвера доступности и отсутствует, когда уровень 4
  действительно открыт (канонический профиль);
- `approved` появится только в D3-D как внешнее событие.

## 4. Канонический термин

| | |
|---|---|
| Пользовательский термин | **«Нужна доработка»** |
| Machine-readable статус | `revision-requested` |

**Запрещено в пользовательском интерфейсе:** «Отклонён», «Rejected», «Провален», «Ошибка отчёта».

Это не наказание и не финальный отказ: работа вернулась к пользователю с конкретным комментарием,
и следующий шаг очевиден — доработать и отправить снова. Тон всех формулировок — спокойный и
рабочий; красный error-state как основной образ статуса запрещён (визуальная ДНК, §7 задания).
Статус **не** окрашивается новым «тревожным» цветом: провизорная палитра не содержит warm/amber
акцента, и состояние передаётся **словами и геометрией** (прецедент DD-232), а не изобретённым
оттенком — финальные цвета остаются за prelanding-палитрой (OQ-1).

## 5. Границы dev/test adapter

`revision-requested` в frontend-only прототипе имеет **единственный источник** — explicit
development/test adapter (прецедент `?scenario`, DD-234/DD-272/DD-273):

- нужен для deterministic screenshots и будущих E2E;
- **не** является пользовательским действием и не появляется ни в одной пользовательской ссылке;
- **не** включается автоматически — ни по таймеру, ни по факту отправки;
- **не** изменяет production progression: он пишет только report-workspace, никогда —
  `ata.lesson-progress.v1`;
- **не** может выдать `approved` (это D3-D) — неизвестное значение вердикта fail closed;
- feedback, который он подставляет, — **provisional development/test content** и явно так помечен.

Точная форма адаптера решена в D3-C-B (DD-291): query-параметр `?verdict=revision-requested`
рядом со `?scenario=report`; контракт выше соблюдён.

## 6. Хранилище: `ata.report-workspace.v2`

Появление вердикта и feedback меняет схему, а изменение схемы получает **новый ключ**, не тихую
миграцию по месту (`REPORT_STORAGE.md` §2).

### 6.1 Будущая схема v2 (контракт, код в D3-C-A не пишется)

```jsonc
{
  "version": 2,
  "reports": [
    {
      "levelCode": "level.003",
      "entries": [ /* ровно entryCount записей — как в v1 */ ],
      "summary": "",
      "status": "draft",              // "draft" | "pending-review" | "revision-requested"
      "submittedAt": null,
      "revision": 0,
      "meaningfulRevision": 0,        // D3-C-B (DD-290): содержательные изменения; atRevision пинит его
      "review": null                  // объект при "revision-requested"; при "pending-review" — история resubmit
    }
  ]
}
```

Форма `review` (минимальная, §7):

```jsonc
{
  "comment": "…",                     // один общий комментарий проверки
  "sections": ["report.003.entry.3.noticed", "report.003.summary"],
  "receivedAt": "…",                  // ISO; как submittedAt — не рендерится
  "atRevision": 4                     // счётчик revision на момент вердикта —
                                      // от него выводится «есть изменения после вердикта»
}
```

Инварианты v1 сохраняются: `approved` в статусе — подделка, запись отбрасывается; section ID вне
известного множества секций уровня — отбрасывается **этот ID**, а не работа пользователя; `review`
при статусе `draft`/`pending-review` — отбрасывается объект review; подделка может стоить только
черновика и **никогда** не откроет уровень и не сфабрикует вердикт.

### 6.2 Миграция v1 → v2 (правила; код — D3-C-B)

Безопасная **односторонняя** миграция валидных данных:

1. валидный v1-`draft` переносится как `draft`;
2. валидный v1-`pending-review` переносится как `pending-review`;
3. содержимое всех пяти записей и итогового наблюдения сохраняется дословно;
4. `review` у мигрированных записей — `null` (в v1 вердикта не существовало);
5. **v1 не удаляется автоматически** — ключ `ata.report-workspace.v1` остаётся на месте;
6. битые или неизвестные v1-данные **fail closed** — v2 начинается пустым, v1 не трогается;
7. **никакого молчаливого уничтожения валидного черновика**: если v2 уже содержит запись уровня,
   существующая v2-запись побеждает (миграция не перезаписывает более новую работу);
8. миграция выполняется при чтении, детерминирована и идемпотентна.

## 7. Минимальная структура feedback

Для D3-C feedback — это ровно:

- **один общий комментарий проверки** (текст);
- **список section IDs**, требующих внимания.

Section IDs уровня 3: `report.003.entry.{1..5}.{when|decided|noticed}` и `report.003.summary`.
Raw ID **никогда не показываются** пользователю — интерфейс переводит их в понятные указатели
(«Запись 3 · Что заметил после сделки», «Итоговое наблюдение»).

**Не входит:** имя проверяющего · avatar · countdown · чат · секционные треды · rubric score ·
торговая оценка · финансовые значения.

Feedback в прототипах и dev/test adapter — **provisional development/test content**, явно помечен
и не является canonical curriculum content (класс риска DD-268: выдуманная торговая оценка —
псевдо-методология). Канонический пример нейтрального provisional feedback:

> «Уточните, какое условие было записано до входа, и свяжите итоговое наблюдение со всеми пятью
> записями.»

## 8. Scope D3-C-A

Определить визуальное и продуктово-архитектурное направление для `revision-requested` и resubmit
**внутри выбранного Evidence Ledger** (DD-271 не отменяется, композиция ледгера не пересматривается):

- где живёт общий комментарий проверки;
- как отмечаются разделы, требующие внимания, и как пользователь понимает, что можно исправить;
- чем `revision-requested` отличается от `draft` и `pending-review`;
- как выглядит повторная отправка и как сохраняется спокойный, некарательный тон;
- что происходит с уже отправленной версией; как объяснено browser-local ограничение;
- mobile-поведение;
- как экран **не** превращается в dashboard, inbox или ticketing.

Артефакты D3-C-A: этот документ · `D3_REVISION_ART_DIRECTION.md` (три структурно разных
направления) · статические прототипы (`design-memory/proposals/d3-revision/`) · screenshots
(`design-memory/screenshots/d3-revision/concepts/`) · self-review
(`docs/visual-reviews/D3_C_REVISION_ART_DIRECTION.md`) · DD-282…DD-288.

## 10. Acceptance criteria D3-C-B (будущая реализация)

Реализация D3-C-B считается принятой, когда:

- [ ] хранилище переведено на `ata.report-workspace.v2` с миграцией по правилам §6.2,
      закреплённой тестами (включая «v1 не удаляется», «битое — fail closed», «существующая
      v2-запись побеждает»);
- [ ] статус `revision-requested` попадает в состояние только через explicit dev/test adapter (§5);
      никакой пользовательский путь его не создаёт; unknown verdict → fail closed;
- [ ] в статусе `revision-requested` показываются: чип «Нужна доработка», общий комментарий,
      указатели на отмеченные разделы **без raw section IDs**;
- [ ] все поля снова редактируемы; данные пяти записей и итогового наблюдения не теряются
      при вердикте, правке и повторной отправке (закреплено тестом);
- [ ] resubmit доступен по правилу §2 (готовность ∧ изменения после вердикта), требует
      подтверждения (конструкция DD-277) и возвращает статус ровно в `pending-review`;
      формулировка «Отправить наставнику» по-прежнему запрещена;
- [ ] фраза о закрытом уровне 4 остаётся выведенной из резолвера; `ata.lesson-progress.v1`
      не пишется ни в одном состоянии цикла;
- [ ] запрещённые термины («Отклонён», «Rejected», «Провален», «Ошибка отчёта») отсутствуют;
      закреплено тестом на копирайт;
- [ ] browser-local правда сформулирована и в revision, и после resubmit;
- [ ] mobile: Evidence Ledger сохранён; CTA resubmit не перекрыт bottom navigation
      (геометрическая проверка bounding boxes ≥12px, прецедент DD-281) на 390×844, 320×720,
      200% zoom; длинный feedback не ломает layout; sticky submit поверх полей отсутствует;
      bottom sheet для основного feedback отсутствует;
- [ ] `?scenario=report` остаётся единственным пользовательски-невидимым входом в историю;
      canonical marker не изменён;
- [ ] пройден `ata-visual-qa-loop` + `ata-anti-generic-ui-review` + heuristic audit;
      реальные screenshots по протоколу.
