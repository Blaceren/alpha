# REPORT_STATE_MACHINE — lifecycle отчёта (D3-B; revision-цикл D3-C)

Владельцы: `src/features/report-level/model/report-experience.ts` (derivation) и
`src/features/report-level/model/report-workspace-v2.ts` (хранимые статусы и переходы).
Компоненты читают выведенное состояние отсюда и **не переопределяют ни одного правила** (принцип
DD-256 / DD-262, применённый к отчёту).

---

## 1. Lifecycle

```
        ┌──────────────────────── withEntryField / withSummary ───────────┐
        │                                                                 │
        ▼                                                                 │
    ┌───────┐   readiness rule satisfied    ┌───────┐   confirm + submit  │
    │ draft │ ───────────────────────────▶  │ ready │ ──────────────────▶ ┴ ┌────────────────┐
    │       │ ◀───────────────────────────  │       │                       │ pending-review │
    └───────┘   readiness rule broken       └───────┘                       └────────────────┘
                                                                                    │
                                                                                    ✗
                                                                  approved / rejected НЕ существуют
```

| Состояние | Природа | Смысл |
|---|---|---|
| `draft` | **хранится** | отчёт пишется |
| `ready` | **вычисляется** | правило готовности выполнено; ничего не хранится |
| `pending-review` | **хранится** | пользователь отметил отчёт отправленным **в этом браузере** |

`ready` намеренно **не персистится**: это утверждение о записях, и вывод его из записей исключает
ситуацию, когда флаг расходится с тем, что описывает.

**D3-C добавил цикл доработки** (термин пользователя — «Нужна доработка», DD-284):

```
pending-review ──(dev/test verdict adapter, DD-291)──▶ revision-requested ──▶ editing (те же поля)
      ▲                                                        │
      └────────── withResubmitted (готовность ∧ изменение) ────┘
```

| Состояние D3-C | Природа | Смысл |
|---|---|---|
| `revision-requested` | **хранится** (+`review`) | проверка вернула работу; поля снова редактируемы |
| `editing-revision` | **вычисляется** (mode `revision`) | пользователь правит тот же отчёт |
| `ready-to-resubmit` | **вычисляется** | готовность (DD-274) ∧ `meaningfulRevision > review.atRevision` (DD-292) |

Whitespace-правка (нормализация не меняет значение) автосохраняется, но изменением не считается.
Отмеченные секции — направление внимания, **не валидатор**. Resubmit возвращает ровно в
`pending-review`; `review` сохраняется как тихий исторический контекст.

`approved` / `rejected` **не введены** — производны от вердикта наставника, которого не существует и
который **не имитируется** (DD-265, DD-287). D3-D — отдельный будущий этап (`D3_REPORT_SCOPE.md` §2).

## 2. Правило готовности — prototype-only

```
ready ⇔ каждая из 5 записей имеет непустое «Что заметил после сделки»
        ∧ «Итоговое наблюдение» непусто
```

Поля «Когда» и «Что решил» — **необязательный контекст**: требовать их значило бы выдумать rubric,
которой у curriculum нет.

Это **структурная** проверка. Она **не** mentor rubric, **не** торговая оценка, **не** измерение
качества отчёта и **не** обещание одобрения (DD-268, DD-274). Она отвечает на один вопрос: «есть ли
что проверять?».

Пробелы считаются пустотой (`trim()`).

**Показывается словами, никогда цифрой качества:**

- `Заполнено 3 из 5 записей`
- `Осталось заполнить 2 записи и итоговое наблюдение`
- `Можно отправить на проверку`

Никаких процентов, score, grade, quality meter. Никаких красных ошибок до попытки submit.
Русские склонения — `pluralRu` (1 запись / 2 записи / 5 записей).

## 3. Mode — как ведёт себя рабочая поверхность

| Mode | Условие | Поведение |
|---|---|---|
| `editing` | уровень 3 — текущий шаг | живая работа: поля редактируемы, submit доступен по готовности |
| `pending` | статус `pending-review` **и** уровень не пройден | read-only, статус «На проверке», CTA убран |
| `archive` | последовательность уже прошла уровень 3 | read-only; показано только то, что есть в этом браузере |

**Приоритет:** `availability === "completed"` **побеждает** локальную запись.

Это ключевое правило изоляции: pending-отчёт, записанный под dev-сценарием `report`, не должен делать
уровень 3 незавершённым для пользователя, которого последовательность уже провела дальше. Черновик не
может понизить progression, который пользователь уже заработал (DD-271).

## 4. Progression — уровень 4

Фраза о закрытом уровне 4 **выводится**, а не хардкодится:

```ts
nextLevelLocked = resolveRouteAvailability(4, marker, session) === "locked"
blockedNote     = nextLevelLocked ? `Уровень 4 «…» откроется после одобрения отчёта.` : null
```

| Маркер | `levelProgressState(4)` | `lessonAvailability(4)` | blockedNote |
|---|---|---|---|
| `report` (currentLevel 3) | `available` («следующий в очереди») | **`locked`** | показывается |
| `active` (currentLevel 18) | `completed` | `completed` | **отсутствует** |

Резолвер **не изменялся**. Уровень 4 остаётся закрытым при маркере `report` не потому, что отчёт его
«запер», а потому, что уровень 3 **никогда не завершается**: `pending-review` не пишет
`ata.lesson-progress.v1`. Отчёт не закрывает ничего — он просто не открывает.

Для канонического пользователя уровень 4 действительно открыт, и утверждение обратного было бы ложью,
которую пользователь видит. Поэтому фраза **отсутствует**, а не становится ложной.

## 5. Submit

```
canSubmit ⇔ mode === "editing" ∧ isReportReady(draft)
```

`withSubmitted(draft, submittedAt)`:
- отказывает, если `status !== "draft"` (второй submit не переставит время);
- отказывает, если правило готовности не выполнено — `pending-review` **не может** описывать
  незаконченный отчёт;
- время **инжектируется** на границе (компонент), модель остаётся детерминированной.

После submit `withEntryField` / `withSummary` возвращают тот же объект: pending read-only **по
конструкции**, а не только по атрибуту `readOnly`, который вызывающий может забыть.

## 6. Подтверждение

Submit необратим в этом прототипе: нет `rejected`, нет `resubmit`, нет наставника, который вернёт
работу. Поэтому переход требует явного подтверждения, называющего четыре вещи:

1. редактирование будет заблокировано в этом прототипе;
2. отчёт отмечается отправленным **только в этом браузере** — серверной синхронизации нет;
3. уровень 4 останется закрыт (когда это правда — фраза та же выведенная);
4. автоматического одобрения нет: проверка наставником не подключена.

Действия: **«Продолжить редактирование»** · **«Отметить как отправленный»**.
Формулировка «Отправить наставнику» **запрещена** — она была бы ложью (DD-266).

## 7. Копирайт pending

- статус: **«На проверке»** (холодный синий, **не** красный — это не ошибка);
- **«Обычно проверка занимает до одного дня.»** (DD-071);
- **«Отчёт отмечен как отправленный только в этом браузере. Серверная проверка пока не подключена.»**
- **«Уровень 4 «Контрольная точка $50» откроется после одобрения отчёта.»** (выведено)
- выходы: «К списку уроков» · «Посмотреть Путь» — у ожидания есть занятие, pending не тупик.

**Запрещено:** countdown · avatar наставника · имя проверяющего · автоматический вердикт · пульсация
точки статуса (читалась бы как countdown).

## 8. Approved — терминальный вердикт (D3-D, DD-297)

Хранимая машина расширяется одним терминальным переходом:

```
pending-review → approved
```

и существующим путём `revision-requested → …resubmit… → pending-review → approved`.

`approved` **терминален**: поля read-only по конструкции (`withEntryFieldV3`/`withSummaryV3`
возвращают тот же объект), resubmit невозможен, revision-adapter не применяется, повторный approved —
no-op; `review` сохраняется как история; `approvedAt` хранится, но пользователю не показывается; XP
не меняется.

Переход выполняет **только** dev/test-adapter `?verdict=approved` (DD-298): `scenario === "report"`
∧ статус `pending-review` ∧ отчёт ready ∧ вердикт не применён; resubmitted pending-review с
сохранённым review допускается. Ни пользовательского href с `scenario`/`verdict`, ни кнопки
«Одобрить», ни автоматического approved. При storage failure отчёт **остаётся** `pending-review` —
без фальшивого успеха.

### Base-completed vs approval-induced (DD-300)

Presentation approved **не** определяется одним итоговым `completed`. Вычисляются **base** (marker +
обычная сессия) и **effective** (после augmentation) availability:

- **canonical completion** (base уже `completed`, Артём L18) → нейтральный archive: локальный approved
  **не** переименовывает уровень, «Одобрено» и approved-CTA **не** показываются;
- **approval-induced** (base current/available ∧ status approved) → approved archive, «Одобрено»,
  ledger read-only, следующий шаг → `/path`.

## 9. Копирайт approved (D3-D)

- статус-чип: **«Одобрено»** (спокойный, семья успеха — green, DD-284; не красный);
- строка: **«Отчёт принят. Уровень 3 завершён.»**;
- browser-local/provisional пояснение (`dev/test · provisional`), без обещания серверной проверки;
- если есть `review` — тихий блок **«Комментарий последней проверки»** (без ссылок, кромок,
  pass-counter);
- следующий шаг: **«Уровень 4 · Контрольная точка»**, **«Требуется: Баланс Pocket от $50»** (только
  цель);
- primary CTA **«Посмотреть Путь» → `/path`**; secondary **«К списку уроков» → `/lessons`**.

**Запрещено:** баланс Pocket · внесённая сумма · остаток · progress % · Pocket CTA/link · XP · mentor
identity/avatar · countdown · celebration hero · confetti · большая зелёная поверхность · dashboard-
card справа · rubric/score/grade. `approvedAt` не показывается.
