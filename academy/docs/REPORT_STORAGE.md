# REPORT_STORAGE — browser-local report persistence (D3-B; схема v2 — D3-C)

Владельцы: `src/features/report-level/model/report-workspace-v2.ts` (актуальная схема v2, миграция),
`src/features/report-level/model/report-draft.ts` (легаси-схема v1 — только чтение при миграции),
`src/features/report-level/model/report-review.ts` (review-модель и section ids),
`src/features/report-level/model/report-store.ts` (порт хранилища),
`src/features/report-level/hooks/use-report-draft.ts` (autosave).

> **D3-C: актуальный ключ — `ata.report-workspace.v2`** (DD-285/DD-290). Запись v2 добавляет
> `status: "revision-requested"`, объект `review {comment, sections, receivedAt, atRevision}` и
> счётчик `meaningfulRevision` (растёт только при содержательном изменении; `revision` остаётся
> техническим ключом autosave). Миграция — при чтении, односторонняя, идемпотентная: валидный v2
> авторитетен; битый v2 fail closed **без отката к v1**; v1 читается только при отсутствии v2 и
> **никогда не удаляется и не перезаписывается**. Инварианты fail-closed v1 (§4) действуют и в v2;
> дополнительно: forged `approved`/`rejected` → запись отброшена; битый `review` → вердикт отброшен,
> работа сохранена как `pending-review`; неизвестный section ID → отброшен только ID. Разделы ниже
> описывают v1-схему как основание — она остаётся точной для легаси-чтения.

---

## 1. Что это и чем не является

**Это** честная browser-local запись отчёта, который пишет пользователь.

**Это не** backend persistence. Ничего никуда не отправляется, ничего не синхронизируется, ни один
наставник этого не видит, сервера нет. `pending-review` означает ровно «пользователь отметил отчёт
отправленным в этом браузере» и ничего больше (DD-265, DD-266).

## 2. Ключ и версия

| | |
|---|---|
| Ключ | **`ata.report-workspace.v1`** |
| Версия в payload | `1` |
| Хранилище | **`localStorage`** |

**Почему `localStorage`, а не `sessionStorage`** (сознательное расхождение с DD-255): потеря отметки
«досмотрел 50%» — неудобство, видео пересматривается; потеря черновика отчёта — **потеря работы
пользователя**. Autosave поверх `sessionStorage` был бы обещанием, которого хранилище не выполняет.

Ключ версионирован: изменение схемы получает **новый ключ**, а не тихую миграцию. Ключ отчёта
изолирован от `ata.lesson-progress.v1` — они не пересекаются и не читают друг друга (проверено тестом).

## 3. Схема

```jsonc
{
  "version": 1,
  "reports": [
    {
      "levelCode": "level.003",      // канонический код уровня — единственный id (DD-264)
      "entries": [
        { "id": "report.003.entry.1", "ordinal": 1,
          "when": "", "decided": "", "noticed": "" }
        // ровно entryCount записей
      ],
      "summary": "",
      "status": "draft",             // "draft" | "pending-review"
      "submittedAt": null,           // ISO-строка локальной отправки; никогда не рендерится
      "revision": 0                  // монотонный локальный счётчик записей
    }
  ]
}
```

**Не хранится никогда:** XP, баланс, депозиты, любые финансовые значения, торговые результаты,
секреты, ключи сценариев, состояние навигации. Закреплено тестом, который проверяет сериализованный
payload на подстроки.

`ready` в схеме **отсутствует** намеренно: это вычисляемое presentation-состояние
(`REPORT_STATE_MACHINE.md`). Хранение сделало бы возможным расхождение флага с записями, которые он
описывает.

`approved` / `rejected` / `revision-requested` отсутствуют, потому что требуют вердикта наставника,
которого нет. Значение статуса вне союза `draft | pending-review` считается подделкой.

## 4. Нормализация — fail closed

`parseReportWorkspace` **никогда не бросает** и никогда не возвращает мусор.

| Вход | Результат |
|------|-----------|
| `null` / `""` / не строка | пустой workspace |
| Битый JSON | пустой workspace |
| Не объект / массив / примитив | пустой workspace |
| `version !== 1` | пустой workspace |
| `reports` не массив | пустой workspace |
| `levelCode` не парсится | запись отброшена |
| `levelCode` — **не** report-уровень | запись отброшена |
| `status` вне союза (в т.ч. `approved`) | **запись отброшена целиком** |
| 0 / 4 / 6 / 9 записей | нормализуется ровно в `entryCount` |
| Подделанные `id` записей | **id регенерируются** из ordinal |
| Неизвестные поля | не переживают round-trip |
| Нестроковые значения полей | приводятся к `""` |
| Дубликаты по `levelCode` | остаётся первый |
| `revision` отрицательный/дробный | `0` |
| `pending-review` + неполный отчёт | **понижается до `draft`** |

Последнее правило — единственное, где мы не отбрасываем: `pending-review` на незавершённом отчёте не
мог быть создан `withSubmitted`, и честное прочтение — «он никогда не был отправлен». Возвращаем
редактируемый черновик, а не запираем пользователя в его же незаконченной работе.

**Инвариант:** подделанное значение может стоить пользователю только его черновика. Оно **никогда** не
откроет уровень и **никогда** не сфабрикует вердикт.

## 5. Границы длины

`MAX_FIELD_LENGTH = 2000` на поле. Это **не продуктовое правило** и никогда не показывается как лимит:
оно существует, чтобы враждебное или сбойное значение не заполнило квоту origin и не уронило маршрут.

## 6. Порт хранилища

| Реализация | Когда | `durable` |
|---|---|---|
| `BrowserLocalReportStore` | есть рабочий `localStorage` | `true` |
| `MemoryReportStore` | SSR, заблокированное хранилище, storage без методов | `false` |

`createReportStore()` **проверяет форму** storage (`getItem`/`setItem`/`removeItem` — функции), а не
его наличие: `window.localStorage` не гарантированно является настоящим `Storage`. В связке
jsdom/Node, на которой тестируется проект, он оказывается объектом-заглушкой без методов — проверка на
truthiness вернула бы его, и каждый вызов бросал бы исключение.

`write()` возвращает `boolean`. Отказ (квота, заблокированный origin) **сообщается**, а не
проглатывается: интерфейс говорит правду вместо того, чтобы делать вид, что сохранил.

SSR: `localStorage` не читается никогда — сервер всегда рендерит пустой черновик, клиент подменяет
после гидратации через `useSyncExternalStore` (прецедент `LessonSessionGate`, DD-256). Hydration
mismatch отсутствует.

## 7. Autosave

| Состояние | Копирайт |
|---|---|
| `saved` | `Черновик сохранён в этом браузере.` |
| `dirty` | `Есть несохранённые изменения.` |
| `saving` | `Сохраняется в этом браузере.` |
| `unavailable` | `Локальное сохранение недоступно.` |

- Debounce **600 мс** — пишем, когда набор текста успокоился, а не на каждый render.
- Ключ эффекта — счётчик `revision`, а не объект черновика: изменение идентичности не стоит записи.
- `saving` мгновенно по природе: `localStorage` синхронен, и мы **не подделываем задержку** ради
  видимости спиннера — это был бы фальшивый backend loading state.
- Отказ записи даёт `unavailable`, а **не** `dirty`: это не «несохранённые изменения, подожди», а
  «локальное сохранение не работает».

**Запрещённые формулировки:** «Сохранено на сервере», «Синхронизировано», «Отправлено наставнику»,
«Наставник получил отчёт». Закреплено тестами (unit + E2E).

## 8. Изоляция от канонического профиля

Report store **не участвует** в резолвере доступности. Уровень 3 никогда не записывается в
`ata.lesson-progress.v1`, поэтому:

- уровень 4 остаётся закрытым при маркере `report` **автоматически** — не потому, что отчёт его
  «запер», а потому, что уровень 3 не завершён;
- pending-отчёт **не может** задним числом закрыть уровни 4–18 канонического пользователя;
- статус отчёта **не показывается** на уровне, который последовательность уже прошла (Library, Path и
  сам маршрут применяют одно правило: `availability === "completed"` побеждает локальную запись).

См. `REPORT_STATE_MACHINE.md` §4 и DD-271.

## 9. Storage v3 — approved (D3-D, DD-296)

Схема получает **новый ключ**, а не тихую in-place миграцию:

```
v1  ata.report-workspace.v1  — draft | pending-review                (D3-B)
v2  ata.report-workspace.v2  — + revision-requested, review          (D3-C)
v3  ata.report-workspace.v3  — + approved, approvedAt                 (D3-D)
```

Минимальная запись v3: `levelCode`, `entries`, `summary`, `status`
(`draft|pending-review|revision-requested|approved`), `submittedAt`, `revision`,
`meaningfulRevision`, `review`, `approvedAt: string | null`.

### Чтение (односторонняя read-time миграция v1 → v2 → v3)

1. Есть v3 → читать только v3; битый v3 fail closed, **без** отката к v2/v1.
2. Нет v3 → валидный v2 (сам поднимающий v1 при отсутствии v2) поднять в v3 дословно, `approvedAt =
   null`.
3. v1/v2-парсеры **не тронуты**: подделанный `approved` в v2-ключе по-прежнему отвергается v2-
   парсером до подъёма.
4. v1/v2 не удаляются и не перезаписываются; `clear()` v3-store стирает **только** v3; первая
   пользовательская запись после подъёма пишет только v3.

### Нормализация approved (fail closed, но работа сохраняется)

Approved допустим только когда: report-level существует, статус `approved`, отчёт structurally ready,
`submittedAt` валиден, `approvedAt` — валидный ISO timestamp. Иначе:

| Случай | Результат |
|--------|-----------|
| approved + missing `submittedAt` | → `draft` (работа сохранена, progression не открывается) |
| approved + невалидный/отсутствующий `approvedAt` | → `pending-review` (сохранены и работа, и `review`) |
| approved + неполный отчёт | → `draft`, progression не открывается |
| unknown review section ids | отбрасываются поодиночке (не работа) |
| unknown/forged статус (`rejected`, `auto-approved`, …) | запись не становится approved и не открывает L4 |

Валидный пользовательский текст **не** уничтожается из-за битой verdict-метаданной.

### Честная граница (DD-299)

Structurally valid browser-local approved — **provisional frontend prototype state**, не
аутентифицированная backend-истина. Подписи/токены/хеши не добавляются (их проверял бы тот же
клиент — это не security boundary). Реальный authoritative mentor verdict потребует backend.

## 10. Progression augmentation (D3-D, DD-297)

Completion L3 **выводится** из workspace, `ata.lesson-progress.v1` **не пишется**. Чистый слой
`report-progression.ts`: `approvedReportLevelNumbers(workspace)` и `sessionWithApprovedReports(session,
workspace)` (через канонический `withCompletedLevel`) проецируют completion на сессию; существующий
резолвер открывает следующий уровень. Второго store / route-resolver / ключа completion нет;
augmentation идемпотентна и никогда не понижает progression. Подключено в report route/experience,
Lessons Library, Path; **не** в Home.
