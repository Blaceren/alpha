# CRM_PRODUCTION_SESSION_BOUNDARY.md — режим выполнения, прокси сессии и граница доступа

Зафиксировано срезом «DEV CRM Integration Slice 1». Описывает, как CRM определяет
режим работы, как получает сессию сотрудника и что именно закрыто до появления
API данных.

## 1. Контракт режима выполнения

Две переменные, обе **только серверные** (без префикса `NEXT_PUBLIC_`, поэтому ни
одна не попадает в браузерный бандл):

| Ключ | Значения | Когда обязателен |
| --- | --- | --- |
| `CRM_MODE` | `mock` \| `api` | Всегда |
| `CRM_BACKEND_ORIGIN` | абсолютный http(s)-origin | Только при `CRM_MODE=api` |

Правила:

- **Значения по умолчанию нет.** Отсутствующий или неизвестный `CRM_MODE` — это
  ошибка конфигурации (`CrmConfigurationError`), а не повод тихо включить mock.
  Прежний `NEXT_PUBLIC_CRM_MODE` был браузерным и на любом мусоре откатывался в
  `mock`; для переключателя «синтетические данные или реальные сотрудники»
  fail-open недопустим.
- При `CRM_MODE=mock` значение `CRM_BACKEND_ORIGIN` **не читается и не
  валидируется** — устаревшее значение в окружении не может ни на что повлиять.
- В браузер уходит только строка `"mock"` или `"api"` — обычный сериализуемый
  проп от серверного layout (`src/app/(crm)/layout.tsx`) к `AppShell`. Origin
  backend в клиентский код не передаётся никогда.
- Режим не хранится в localStorage.

Валидация origin (`src/config/backend-origin.ts`) отклоняет: пустое значение,
относительный URL, протокол кроме http/https, credentials, query, hash,
непустой путь, некорректный порт. Один завершающий слэш нормализуется.

`next.config.mjs` — это ESM JavaScript, он не может импортировать TypeScript,
поэтому повторяет те же правила отдельно. Источником истины считается
`src/config/backend-origin.ts`, а `src/config/next-rewrites.test.ts` импортирует
**настоящий** конфиг и фиксирует одинаковое поведение обоих.

> Режим считывается серверным компонентом на этапе пререндера, поэтому для
> статически сгенерированных маршрутов он фиксируется при сборке. Практическое
> следствие: сборка выполняется отдельно под каждый режим (обе проверяются в
> гейтах — `CRM_MODE=mock npm run build` и `CRM_MODE=api … npm run build`).

## 2. Точный rewrite

При `CRM_MODE=api` добавляется **ровно шесть** явных внешних rewrite (по одному
осознанному решению на каждый проверенный путь):

```
/api/crm/v1/session               →  ${CRM_BACKEND_ORIGIN}/api/crm/v1/session
/api/crm/v1/users                 →  …/api/crm/v1/users
/api/crm/v1/users/:userId         →  …/api/crm/v1/users/:userId
/api/crm/v1/users/:userId/notes   →  …/api/crm/v1/users/:userId/notes
/api/crm/v1/owner-candidates      →  …/api/crm/v1/owner-candidates
/api/crm/v1/users/:userId/owner   →  …/api/crm/v1/users/:userId/owner
```

При `CRM_MODE=mock` список rewrite пустой. `:userId` — ровно один сегмент;
`/notes` и `/owner` — терминальные, поэтому их дочерние пути не проксируются.

**Почему нет wildcard.** Ни `/api/crm/v1/:path*`, ни `/api/:path*`: шаблон открыл
бы через origin CRM каждый существующий и каждый будущий маршрут backend,
включая те, которые для этого никто не проверял. Расширение проксирования должно
быть отдельным осознанным решением, а не побочным эффектом. Тест
`next-rewrites.test.ts` проверяет, что в `source` нет ни `:path`, ни `*`, и что
список источников равен ровно этим шести путям.

Из этого следует остальное:

- **Cookie остаётся host-only.** Браузер обращается к собственному origin CRM,
  подмены домена не происходит, `Domain`-переписывание cookie не нужно и не
  делается.
- **CORS не настраивается** — запрос одностороннего происхождения.
- Клиент отправляет `credentials: "same-origin"` и `cache: "no-store"`.
- **CSRF-защита для этого endpoint не требуется**: это `GET`, он ничего не
  изменяет и не устанавливает `Set-Cookie`. Логики переписывания cookie нет.
- Проксируются только запросы к сессии; auth- и csrf-маршруты backend через CRM
  недоступны (проверяется E2E: посторонние пути отвечают 404).

## 3. Сессия сотрудника

`GET /api/crm/v1/session` возвращает DTO, который проходит строгую схему Zod
(`src/domain/identity/session-dto.ts`): девять канонических ролей, восемь
канонических разрешений, без дубликатов, `permissionVersion` — целое
положительное, `expiresAt` — ISO datetime, `employeeId` — непрозрачная непустая
строка (формат намеренно не проверяется). Схема `.strict()`: любое лишнее поле —
например `email`, `id`, `xp` — приводит к отказу, а не к тихому проносу данных
в клиент.

Отображение результатов:

| Ответ | Состояние |
| --- | --- |
| 200, схема пройдена | `authenticated` |
| 200, схема не пройдена / не JSON | `malformed_response` |
| 401 | `unauthenticated` → `router.replace("/login?reason=session_required")` |
| 403 | `forbidden` → «Нет доступа к CRM» |
| 5xx, сетевая ошибка, таймаут (8 с), abort | `upstream_unavailable` → повтор |

Fallback-сессии нет. Fallback на `crm_admin` нет. Fallback на mock нет.

Из тела ошибок 401/403 берётся только `requestId` (как код обращения).
`messageKey` backend намеренно не показывается пользователю. Авторитетным
остаётся статус-код. Сырые тела ответов и тексты исключений не логируются и не
рендерятся.

## 4. effectivePermissions — авторитет UI

Аффордансы интерфейса проверяются через `session.effectivePermissions`
(`sessionGrants`), а не пересчитываются из роли.

- **api**: список приходит только из DTO backend.
- **mock**: список заполняется из локальной матрицы `ROLE_PERMISSIONS`, поэтому
  поведение mock-режима не изменилось.

Регрессия, закреплённая тестами: backend отвечает `role = crm_admin`,
`effectivePermissions = []` → не появляется ни назначения владельца, ни экспорта,
ни аудита, ни редактирования заметок, ни настроек. Роль ничего не возвращает
локально.

Ролевые правила сознательно сохранены там, где они принадлежат не UI:

- построение mock-сессий;
- ресурсные правила внутри `MockCrmDataProvider` (**не ослаблены**);
- проекции и редактирование данных в domain-слое;
- навигационный канон `SECTION_VISIBILITY`.

Приватность заметок остаётся ресурсной логикой провайдера/backend и из роли в UI
не выводится.

`expiresAt` сохраняется, но **не используется** как клиентское решение о доступе.
`permissionVersion` — только метаданные, не токен.

## 5. CrmContext

`EmployeeSession.employeeId → CrmContext.actorId`,
`EmployeeSession.role → CrmContext.role`.

`actorId` никогда не берётся из `User.id`, из `DEFAULT_MOCK_SESSION` в api-режиме,
из localStorage и не генерируется в браузере.

## 6. Изоляция mock-переключателя ролей

Ключ localStorage `ata-crm.mock-role.v1` читается и пишется только внутри
`MockSessionProvider`, который в api-режиме не монтируется вовсе. В api-режиме:
`setRole` отсутствует (`null`), `RoleSwitch` не рендерится, `mockSessionForRole` и
`DEFAULT_MOCK_SESSION` недостижимы. Подмена ключа в localStorage не меняет ни
роль, ни разрешения, ни `actorId` — это проверяется и unit-тестом, и E2E. Режим
разработки исключения не даёт.

## 7. Честная граница данных

`ApiCrmDataProvider` в этом срезе не создавался. Поэтому:

- api-режим **никогда** не инстанцирует `MockCrmDataProvider` —
  `getCrmDataProvider`/`getCrmMutations` бросают `MockProviderUnavailableError`;
- маршруты фич в api-режиме не монтируются вообще;
- после подтверждённой сессии отображается ограниченное правдивое состояние:
  «Сессия сотрудника подтверждена. Подключение данных CRM будет добавлено
  следующим этапом», с именем сотрудника и безопасной подписью роли.

Не показываются: mock-пользователи, балансы, заметки, аудит, владельцы, счётчики,
JSON-дампы, `employeeId`, список разрешений, `expiresAt`, `permissionVersion`.

Это **временная защитная граница**, а не замена `ApiCrmDataProvider`.

> **Обновление (Frontend CRM User Detail API Slice 2).** Утверждение «все данные
> CRM отложены» больше не действует целиком. Подключены **ровно две**
> production-способности через `ApiCrmDataProvider`:
> список пользователей (`GET /api/crm/v1/users`, маршрут `/users`) и основа
> карточки учащегося (`GET /api/crm/v1/users/{userId}`, маршрут
> `/users/{userId}`). Всё остальное — заметки, владелец, аудит, финансы,
> активность, таймлайн, полный User 360 — по-прежнему отложено, а
> `MockCrmDataProvider` в api-режиме по-прежнему недостижим. Подробности:
> `docs/CRM_API_USERS_READ.md` и `docs/CRM_API_USER_DETAIL_READ.md`.

Mock-режим продолжает рендерить полный mock-CRM ровно как раньше.

Вход (`/login`) остаётся заглушкой вне границы api-сессии: настоящая
аутентификация сотрудников, SSO и refresh-токены в этот срез не входили.

## 8. Тестовая топология

Настоящий backend в этой фазе **не запускался**: у него ещё нет ни DEV-базы, ни
окружения. БД, миграции и сервисы не затрагивались.

Для E2E используется детерминированный тестовый stub на стандартной библиотеке
Node (`tests-e2e-session/support/session-stub.mjs`): слушает только loopback,
реализует единственный маршрут `GET /api/crm/v1/session`, на всё остальное
отвечает 404, отдаёт `Cache-Control: no-store` и завершается вместе с набором
тестов. Нужное состояние ответа выбирается тестовой cookie
`ata_test_crm_session_state` — механизм существует только в харнессе; в
производственном клиенте сессии нет ни тестовых заголовков, ни тестовых
query-параметров.

Порты: CRM api-режима `127.0.0.1:3010`, stub `127.0.0.1:3110`, mock-CRM `3000`.
Один worker — память сервера ограничена.

Оба Playwright-конфига задают режим явно: `playwright.config.ts` → `CRM_MODE=mock`,
`playwright.session.config.ts` → `CRM_MODE=api` + `CRM_BACKEND_ORIGIN`. Ни один не
полагается на значение по умолчанию.

## 11. Расширение схемы прав до десяти значений

CRM User Notes v1 добавил два значения в канонический список прав сессии:
`view_user_notes` и `create_user_notes`. Первые восемь сохраняют прежний
относительный порядок; новые значения добавлены в конец.

- Строгая схема сессии принимает оба новых значения.
- Неизвестное право по-прежнему отклоняется (fail closed).
- Дубликаты по-прежнему отклоняются.
- `permissionVersion` не изменился и сохраняет прежнюю семантику.
- Фронтенд не пересчитывает права из роли — источником остаётся
  `effectivePermissions` от бэкенда.

Производственная карточка пользователя теперь содержит раздел заметок,
ограниченный этими правами. Подключённые возможности: список пользователей,
карточка пользователя, чтение заметок, создание заметки. Владелец, Audit,
финансы, а также редактирование/удаление заметок остаются отложенными.

Подробности: `docs/CRM_API_USER_NOTES.md`.
