# PHASE_1B4_C_ASSIGN_OWNER.md — визуальное ревью

> Phase 1B4-C · Секция «Ответственный и работа» на User 360: назначение/снятие primary owner
> (`assignPrimaryOwner`, кандидаты через `getPrimaryOwnerCandidates`).
> Решения: D-64…D-74. Скриншоты: `screenshots/phase-1b4-c-assign-owner/final/`.
> Реальный рендер, headless Chromium, `npx playwright test owner-assignment`
> (first-pass: `PHASE_1B4C_PASS=first`).

---

## Что ревьюировалось

Вторая мутирующая поверхность в CRM и **первая, которая заменяет** значение, а не добавляет.
Проверялось не «красиво ли», а:

- контрол читается как часть секции «Ответственный и работа», а не как отдельное приложение;
- действие не доминирует над профилем;
- текущий owner (в dl) и невыбранный ещё выбор (в select) не путаются;
- снятие owner («Без ответственного» → «Не назначен») понятно;
- запрещённой роли объяснение подаётся спокойно, без fake-контрола;
- success не выглядит рекламой (toast); conflict честно объясняет, что показаны актуальные данные;
- raw id / диагностика на экран не попадают;
- mobile/tablet/zoom не ломают sticky context-колонку; горизонтального overflow нет.

Персона — Nina Chmiel (`usr_mock_026`), baseline owner «Support 1».

## First pass — находки

### Critical

Нет. Продукт вёл себя корректно на всех проверенных путях (подтверждено E2E, проверяющими
**settled**-состояние).

### Major

**M-1 · Фокус не возвращался на select в реальном браузере.**
После success код вызывал `selectRef.current?.focus()` синхронно сразу после разрешения мутации, но в
этот момент select ещё отрисован `disabled` (флаг pending не «пропечатался»), а браузер молча
отказывается фокусировать disabled-контрол. В component-тесте (jsdom) проходило, в Chromium — нет.
*Исправлено:* фокус перенесён в `useEffect` на переход `pending → success`, когда select снова enabled.
Ключ на переходе статуса, а не на флаге из хендлера, — иначе гонка (submit ставит success до того, как
хендлер выставит флаг).

**M-2 · Скриншот «pending» показывал success.**
Способ удержать pending (busy-wait в `setItem`) был коротким (400 мс) и не гарантировал, что кадр
снят в pending: к моменту `screenshot` мог отрисоваться success.
*Исправлено:* удержание увеличено до 2 с, а снимок делается **после** явного ожидания кнопки с именем
«Сохраняем…». Busy-wait блокирует main thread, но снимок берётся процессом браузера с последнего
отрисованного кадра, поэтому «Сохраняем…» попадает даже при замороженном JS.

**M-3 · Скриншоты «success» и «conflict» ловили окно refetch.**
Баннер («Ответственный обновлён» / «Ответственный уже изменён…») появляется сразу, а поле
«Ответственный» в dl обновляется после refetch `getUser360` (dev-задержка 150 мс). Снимок без
ожидания показывал баннер поверх **старого** владельца — для conflict это прямо противоречит тексту
«показаны актуальные данные».
*Исправлено:* перед снимком тест ждёт, пока dl покажет settled-значение (Retention 1 / Mentor 1).

### Minor

**m-1 · Исторические скриншоты прошлых фаз перерисовались прогоном.**
User 360 теперь содержит owner-форму, поэтому PNG phase-1c/1b4-b изменились; плюс средовой шум
рендера. По процессу исторические скриншоты восстановлены к HEAD (`git checkout`), коммитится только
`screenshots/phase-1b4-c-assign-owner/final/`.

**m-2 · forbidden-скриншот показывает не-baseline владельца.**
В комбинированном тесте reset overlay защищён sessionStorage-guard (чтобы пережить reload), поэтому шаг
forbidden наследует owner предыдущего шага. Не дефект: скриншот демонстрирует именно то, что нужно —
запрещённой роли (support) виден текущий owner и строка-объяснение без контрола. Оставлено как есть.

## Исправлено (critical/major)

- M-1 — фокус после success через effect (правка продукта, `owner-assign-form.tsx`).
- M-2 — pending-скриншот удерживается 2 с и снимается по имени «Сохраняем…» (правка теста).
- M-3 — success/conflict снимаются после settled dl (правка теста).

Все — до финального прогона.

## Оставшиеся minor

- m-1, m-2 выше — процессные/тестовые, продукта не касаются.

## Final pass — проверено глазами (13 финальных PNG)

- **unchanged** — select предзаполнен текущим владельцем «Support 1», «Сохранить» disabled.
  Контрол — часть секции, не доминирует.
- **changed** — select «Retention 1», «Сохранить» активна (accent); в dl всё ещё «Support 1» —
  текущий владелец и невыбранный выбор различимы, не путаются.
- **pending** — кнопка «Сохраняем…» (disabled, `aria-busy`), select disabled; поле ещё «Support 1»
  (запись в полёте).
- **success** — dl «Retention 1», select «Retention 1», спокойная строка «Ответственный обновлён»
  (`role=status`), «Сохранить» снова disabled. Не похоже на toast-рекламу.
- **conflict** — dl «Mentor 1» (победитель гонки), select пересинхронизирован на «Mentor 1», строка
  «Ответственный уже изменён. Показаны актуальные данные.» — текст соответствует показанному.
- **forbidden** — роль Support: контрола нет вовсе, строка «Ваша роль не может менять ответственного»,
  текущий owner виден; заодно видно, что финансы — бакеты, email маскирован (право не расширено).
- **storage-error** — строка «Локальное сохранение недоступно. Попробуйте ещё раз», raw-диагностики нет,
  показан прежний (неизменённый) owner.
- **mobile 390 / 320**, **tablet 1024**, **zoom 200%** — select + «Сохранить» умещаются, touch-target
  ≥44px, sticky/context-колонка не ломается, горизонтального overflow нет.
- **users-consistency** — Users отфильтрованы по «Retention 1», строка Nina Chmiel присутствует, колонка
  «Ответственный» = «Retention 1».
- **today-consistency** — Nina Chmiel в очереди Today с новым владельцем.

Raw employee id (`emp_*`) в видимом тексте секции не встречается ни на одном кадре (значения `<option>`
их несут — это то, что форма отправляет, — но текст на экране только человекочитаемый).
